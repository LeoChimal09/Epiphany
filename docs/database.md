# Database

MySQL 8.4 is Epiphany's source of truth (see [the decision record](decisions/0001-initial-architecture.md)).
The schema lives in code at `packages/core/src/db/schema.ts`; migrations are generated by
drizzle-kit into `packages/core/drizzle/` and applied by Epiphany's own runner.

## Records

| Table            | Holds                                                                         |
| ---------------- | ----------------------------------------------------------------------------- |
| `owners`         | The owner identity (display name, timezone, optional Discord user ID and avatar hash). |
| `categories`     | Categories per owner. The Inbox is the row with `system_key = 'inbox'`.        |
| `tasks`          | Assignments and to-dos. `status` is `open`/`completed`; `archived_at` is separate. `source_text`/`source_ref` link the message it came from; `review_note` flags what needs the owner's eye (cleared when a deadline is set). |
| `events`         | Fixed events. `status` is `scheduled`/`canceled`; nullable `series_id` groups materialized local recurring occurrences. |
| `work_blocks`    | Movable planned time, optionally tied to a task: `planned`/`completed`/`removed`. |
| `notes`          | Notes and ideas, categorized (default Inbox).                                  |
| `preferences`    | Explicit key/value preferences, `proposed` or `confirmed`.                     |
| `action_history` | Append-only changes with source and before/after, written with each change.    |
| `confirmations`  | Proposed consequential actions awaiting confirmation (see [security](security.md)). |
| `discord_overviews` | Which Discord message shows each overview in a server (edited in place, recreated if deleted). |
| `reminders` | Persistent reminder jobs: dedupe key, status, attempts, claim time, and why a job was skipped or failed. |
| `provider_usage` | Monthly spending per provider kind (voice) per owner, separate from the text budget in `ai_usage`. |
| `observations` | Things the owner chose to report about how they work (task durations, snoozes). Only recorded when learning is on; erased on request. |
| `sessions`       | Dashboard sign-in sessions, keyed by a hash of the cookie token.               |
| `calendar_accounts` | A connected Google account (Goal 11): encrypted tokens, `status` (`connected`/`needs_reauth`/`revoked`), granted scopes, last error, and the dedicated Epiphany calendar's ID. A CHECK constraint forbids tokens on any account that is not `connected`. |
| `synced_calendars` | Calendars found in the account. Only `selected` ones are read; the `epiphany` kind is the dedicated one. Holds the incremental sync token, `last_synced_at`, and `sync_status` (`pending`/`ok`/`stale`/`error`). |
| `calendar_event_refs` | Links a Google event to a local record: imported events (`ownership = 'external'`, `event_id`) or work blocks Epiphany wrote (`ownership = 'epiphany'`, `work_block_id`). Keeps ETag, recurring-series ID and original start, last pushed block version, and `sync_state` (`synced`/`pending`/`uncertain`/`conflict`/`remote_deleted`/`removed`/`detached`). |

Design rules:

- IDs are UUID strings. Times are UTC `DATETIME(3)`; every connection sets its session time
  zone to UTC. Display timezones come from the owner/event, never from the database.
- Completing a task, canceling an event, and removing a work block are three separate
  operations (`packages/core/src/db/domain.ts`). Each changes only its own row, keeps the row,
  and writes history in the same transaction. `CHECK` constraints stop MySQL from storing a
  status without its matching timestamp. Cascading work-block cleanup on completion is
  deliberately **not** implemented; it arrives with weekly planning (Goal 14).
- Foreign keys never cascade deletes. Deleting records is a later, confirmed operation.
- `updated_at` and `version` are maintained by the shared services, not triggers. If you edit
  a row by hand in a SQL client, set them yourself.
- Every operation takes the owner and refuses rows belonging to anyone else. Authentication
  and the permission matrix arrive in Goal 04.

## Commands

| Command                  | Purpose                                                                  |
| ------------------------ | ------------------------------------------------------------------------ |
| `bun run db:up`          | Start the local MySQL container (needs `.env`; see local development).    |
| `bun run db:generate`    | Generate a migration from schema changes. Review the SQL before keeping it. |
| `bun run db:migrate`     | Apply pending migrations to `DATABASE_URL`.                              |
| `bun run db:status`      | Show applied and pending migrations and any history problems.            |
| `bun run db:check`       | Fail if `schema.ts` and the migrations disagree. Needs no database.       |
| `bun run db:test:up`     | Start the disposable test MySQL on port 3320 (in-memory data).            |
| `bun run db:test:down`   | Stop it and discard its data.                                             |

There is no `db:push`. Routine app restarts never create tables; migration is an explicit step.

### Local recurring events (0014)

`0014_sweet_omega_red` adds nullable `events.series_id` and an owner/series index;
existing events remain unchanged with a null series ID. Apply pending migrations
before deploying the updated dashboard and worker.

The shared event service validates the full finite recurrence and every local
wall-clock interval before inserting occurrences and history in one transaction.
Each occurrence has its own ID, version, reminders, and calendar synchronization
reference. Rules are retained in creation history; occurrences are not generated
by an in-memory timer and survive restarts. Confirmed cancellation locks the
exact owner-scoped occurrence/series versions, retains rows, and cancels affected
scheduled reminders atomically.

## Connecting with DBeaver

Start the local database (`bun run db:up`), then create a MySQL connection with:

- Host `127.0.0.1`, port `3319`, database `epiphany`
- User `epiphany`, password = `MYSQL_PASSWORD` from your `.env` (`epiphany` with the example defaults)
- DBeaver may show "Public Key Retrieval is not allowed": set the driver property
  `allowPublicKeyRetrieval` to `true` (local connection only).

Run `bun run db:migrate` first, or the database will be empty. Treat DBeaver as a read-mostly
window: manual edits bypass the history table and the `version`/`updated_at` rules above.

## Changing the schema

1. Edit `schema.ts` and run `bun run db:generate`; read the generated SQL.
2. Prefer additive changes. For renames, type changes, or new required columns, stage the
   change across migrations with backfills.
3. Run `bun run db:check` and the database tests (`bun run db:test:up`, then `bun run test:run`
   with `TEST_MYSQL_ADMIN_URL` set; see `.env.example`).
4. Never edit a migration that has been applied anywhere shared. The runner refuses to run
   if an applied file changed or if a pending migration sorts before an applied one; add a new
   corrective migration instead.

## How the runner behaves

- A MySQL named lock (`GET_LOCK`) serializes runners, so a dashboard and worker starting
  together cannot apply the same migration twice. A second runner waits (60 s by default),
  then finds nothing pending.
- Migrations apply in journal order. Each is recorded in `__drizzle_migrations` only after
  all its statements succeed.
- MySQL commits DDL implicitly, so a migration cannot be rolled back as a unit.

## Recovering from a partly applied migration

### Original 0011 checksum

`0011_nebulous_outlaw_kid.sql` must remain the original single ALTER statement with no
trailing newline (SHA-256 `242300bca7673f5399a360ad8ba0682f048d3db4d39d5e14c9dc8a793a733de3`).
The task-type backfill belongs in the later `0013_backfill_task_types` migration,
not in 0011. If your database recorded this original hash, restoring that file allows
normal migration checks to pass; do not edit the database's migration-history hash.
Migration 0012 adds the item-level split-reminder columns required by the dashboard.
Run pending migrations before restarting the updated dashboard and worker.

Railway also applied the verified release `cec7de7` version of 0011, containing the same ALTER
plus that backfill (SHA-256 `bae9bfd4833e56f2b357448350f7d29f036c46124a7600c51d6d581d35bf071a`).
The runner recognizes **only** that exact alternate checksum for the original 0011 tag,
timestamp, and current file hash. It verifies `tasks.task_type` is
`enum('task','todo') NOT NULL DEFAULT 'task'` before allowing pending migrations.
It preserves the recorded hash, skips the already-applied ALTER, and applies 0012/0013
normally; repeating the backfill is idempotent. Local databases with the original checksum
continue through the same pending migrations. Keep the migration pre-deploy command enabled:
repeated runs safely skip applied migrations.

All other checksum changes still block deployment and require investigation.
Checksum-mismatch errors include the database SHA-256, current file SHA-256, and migration
timestamp. Share those lines and the deployment commit when investigating a failed Railway
pre-deploy step; no database credentials or personal records are needed.

If `db:migrate` fails, it prints the migration tag and the failing statement ("statement 2 of
5"). The migration is **not** recorded, but earlier statements in it may have taken effect.

1. Stop other deployments and do not rerun blindly.
2. Run `bun run db:status`; the failed migration is still pending.
3. Compare the real schema (`SHOW CREATE TABLE`) with the migration's SQL to see which
   statements took effect.
4. If the migration has never been applied anywhere else (the normal case), undo its partial
   effects by hand or restore the pre-migration backup, correct the migration file, and run
   `bun run db:migrate` again. If it was applied elsewhere, leave it untouched and add a new
   corrective migration.
5. Run `bun run db:status` and the verification queries; confirm no pending migrations remain.

Before migrating production data, confirm the target, `db:status`, and a restorable backup.
This sequence is exercised by a test (a deliberately failing two-statement migration), against a
disposable database.

## Tests

Database tests create a uniquely named database (`epiphany_test_<hex>`) per test and drop exactly
that database afterwards, then assert it is gone. They are skipped when `TEST_MYSQL_ADMIN_URL` is
unset; set `REQUIRE_DB_TESTS=true` (CI does) to make a missing database a failure.

Limit: there is only one real migration so far, so "upgrade from the previous schema" is
exercised with a synthetic follow-up migration over seeded rows. From the second real migration
onward, add seeded rows for the prior schema and test the real upgrade.
